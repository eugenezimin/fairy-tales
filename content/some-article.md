## Тема встречи

Рассмотрение архитектуры multi-AZ для продукта **Container Apps**: разбор устройства control plane и data plane, схем репликации базы данных, изоляции контейнеров и сценариев хранения состояния пользовательских подов.

## Ключевые решения и обсуждённые архитектурные подходы
### 1. Multi-AZ топология (control plane и data plane)
- **Managed Kubernetes** — основа multi-AZ архитектуры. Worker-ноды распределены по 3 AZ.
- Количество экземпляров подов **не утраивается** при переходе на multi-AZ — поды остаются в прежнем количестве, но равномерно распределяются по AZ через topology spread constraints (scheduler).
- При отказе одной AZ поды переподнимаются в оставшихся AZ. Гарантия отказоустойчивости — при потере **максимум одной AZ**.
- **Load balancer** фронтирует как control plane, так и data plane; трафик поступает сначала на Istio, далее — на микросервисы.
- Между control plane и data plane — компонент **Magic Router**.
- В **data plane** Kafka и message-брокеры отсутствуют; там происходит только создание пользовательских подов через `cluster-gateway`.

### 2. База данных: отказ от Patroni в пользу CloudNativePG
- Первоначально рассматривался **Patroni** с растяжкой на 3 AZ. От этого варианта отказались ввиду его нестабильности на практике (постоянные починки).
- Принято решение использовать **CloudNativePG** с синхронной (sync) репликацией. На stage уже работает. Ночью 23–24 апреля **Artifact Registry** был переведён на multi-AZ CloudNativePG. Помощь в тюнинге оказал Михаил Топоров (команда DBaaS).
- **Причина отказа от async-репликации**: при async-репликации возникал лаг — микросервис Container Apps читал с реплики, которая не успевала получить свежую запись от мастера. Это приводило к ошибке `not found` при попытке запустить образ сразу после создания реестра.
- **Алексей Лицов** уточнил различие понятий: sync-репликация гарантирует наличие записи в другой AZ в рамках одной транзакции; async — не гарантирует. Обсуждение прошло через призму CAP-теоремы (consistency vs. availability).
- **Задержки** при sync-репликации замерялись, но результаты ещё не зафиксированы в документации.

### 3. Изоляция пользовательских контейнеров (kata containers / microVM)
- Пользователь может запустить контейнер:
    - **без root-прав** — стандартный pod.
    - **с root-правами** — внутри пода поднимается **microVM** (вложенная виртуализация, kata containers). Побег из пода приводит на хост microVM, а не на основной гипервизор. Безопасность основного хоста сохраняется.

### 4. Хранение состояния в подах
- **Ephemeral-том** (tmpfs/emptyDir) — данные теряются при падении пода.
- **Persistent volume через CSI-драйвер** — подключение внешнего хранилища (текущий вариант: S3/object storage).
- В перспективе ожидается **NFS-подобный сервис** (разрабатывает команда SDS): Managed Kubernetes планирует написать CSI-драйвер для него. Это позволит пользователям монтировать папки или весь под к внешнему файловому хранилищу за пределами Kubernetes.
- Синхронизация данных между несколькими репликами одного пода **не предусмотрена** — поды изолированы друг от друга.

### 5. Масштабирование пользовательских Container App
- Пользователь сам выбирает стратегию:
    - **Scale-to-zero** — 0 подов в простое, под поднимается при первом запросе (random AZ).
    - **Минимум 1 под** — базовая надёжность.
    - **2–3 пода** — высокая надёжность с распределением по разным AZ.
